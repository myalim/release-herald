# 분류 기준 — `impact` · `weight` · `ko`

> **이 파일이 판정 기준의 SSOT 다.** 요약 생성이 CI 에서 돌므로 기준도 저장소 안에 있어야 하고,
> 스키마가 값의 **형식**을 강제하는 자리라면 여기는 그 **판정**을 갖는다.
> 2026-09-01 에 104항목을 손으로 가르며 굳었고, 그 결과가 `data/summaries.json` 의 시드다.

## 할 일

1. **지시받은 입력 파일**을 읽는다 — 판정할 릴리스 하나가 들어 있다.
2. 각 항목에 `impact` · `weight` · `ko` 를 채운다. **`kind` 와 `en` 은 한 글자도 바꾸지 않는다.**
3. 같은 구조로 **지시받은 출력 파일**에 쓴다. **`Write` 는 한 번만** 한다 — 나눠 쓰면 뒤가 앞을 덮어쓴다.
4. **그 밖의 일은 하지 않는다.**
   - **이 파일과 입력 파일 외에는 아무것도 읽지 않는다** — 필요한 형식은 아래에 전부 있다.
     디렉터리·스키마·기존 `summaries.json` 조사는 판정에 쓸 턴을 먹는다.
   - 커밋도 push 도 워크플로가 한다. 다른 파일을 고치지 않는다.

입력과 출력의 형태 (릴리스는 **항상 하나**다 — 여러 릴리스는 호출이 나뉜다):

```jsonc
// 입력 — 예: data/pending/v2.1.258.json
{ "releases": [ { "version": "v2.1.258", "date": "2026-09-01", "url": "...",
                  "items": [ { "kind": "fixed", "en": "Fixed …" } ] } ] }

// 출력 — 예: data/judged/v2.1.258.json · kind·en 은 그대로, 셋을 더한다
{ "releases": [ { "version": "v2.1.258", "date": "2026-09-01", "url": "...",
                  "items": [ { "kind": "fixed", "impact": "user", "weight": 1,
                               "ko": "…", "en": "Fixed …" } ] } ] }
```

`items` 가 빈 릴리스는 빈 채로 그대로 낸다 — 항목이 0개인 릴리스가 실제로 흔하고, 그 버전이
파일에 존재해야 "볼 것이 없다" 와 "모른다" 가 구분된다.

## `impact` — 판정 질문은 하나다

**"이 사용자가 이걸 몰라서 손해를 보나."** 기능의 크기나 수정의 난이도가 아니라 **닿는 표면**으로 가른다.

`internal` 로 가는 것:

- 특정 실행 환경 한정 — Bedrock · Vertex · Foundry · Enterprise 좌석 · 조직 관리 설정 · SDK · 타 에디터 확장
- 체감되지 않는 성능·크기 개선
- 텔레메트리 내부

**나머지가 `user` 다.** 실측에서 60/40 으로 갈렸다 — `internal` 이 소수라는 뜻이므로, 의심스러우면 `user` 다.

**"사용자" 는 배포 대상의 프로파일이지 평균이 아니다** — 훅·subagent·worktree·Remote Control 을 쓰는
사람에게는 그 표면의 수정이 `user` 이고, 같은 항목이 다른 프로파일에서는 `internal` 일 수 있다.

## `weight` — "몰랐을 때의 손해" 순

- **1** — 보안 · **표면이 넓거나 권한에 닿는** 신기능 · 기본값이나 동작이 바뀜
- **2** — 자주 겪던 버그의 수정 · 눈에 띄는 개선 · 좁은 표면의 부가 기능
- **3** — 나머지 `user` 항목

**화면에는 1 만 뜬다.** 실측에서 릴리스당 2~5개로 수렴했고 그중 다수가 보안 수정이었다.
1 을 후하게 주면 그 수렴이 깨져 화면이 곧 노이즈가 된다.

**"보안" 은 원문이 그 단어를 쓸 때만이 아니다.** 표본 대조에서 놓친 것이 전부 이 형태였다 —
원문에 `security` 가 없고 아래처럼 적혀 있었다. 무엇이 새는가·누가 넘어오는가로 읽는다.

- 자격증명·비밀이 로그·URL·헤더에 노출되던 것을 가림 (`redacted`·`masked`)
- 낮은 신뢰 소스(프로젝트 설정·마켓플레이스·플러그인)가 더 높은 권한의 동작을 켤 수 있던 것
- 권한·거부 규칙·샌드박스·승인 프롬프트가 우회되던 것 (`bypass`·`skipped`·`deny rule not applying`)
- 외부 입력을 막는 강화 (`hardening`·제어문자 거부·path traversal 차단)

**신기능이 전부 1 은 아니다.** `added` 라는 이유만으로 1 을 주면 릴리스당 대여섯 줄이 신기능으로
차서 정작 보안 수정이 밀린다. 선은 **닿는 표면의 넓이**다.

- **1 인 것** — 새 실행 모드·권한 설정(`--restricted`, 작업 디렉터리 밖 읽기 확인), 기본 모델 교체,
  새 화면·패널, 훅 이벤트처럼 그 표면을 쓰는 사람 전체가 영향받는 것
- **2 인 것** — 기존 명령에 붙은 옵션 하나, 설정 키 하나, 특정 출력에 추가된 정보

## `kind` 로 대신할 수 없다

한 접두어 안에 보안 수정과 특정 환경 한정 버그가 함께 들어 있다 — 실측에서 `Fixed` 가 전체의 64%였다.
**접두어는 사실이고 이 판정은 해석이다.**

## `ko` — 화면에 그대로 뜨는 문장

- **80자 상한이 계약이다** — 검증이 잡으므로 넘기면 생성이 실패한다.
- 원문 한 항목이 두 가지를 말하면 **주된 것만** 남긴다. 나머지는 `en` 이 갖는다.
- 옵션명·플래그·이벤트명은 원문 표기 그대로 백틱 안에 둔다 — 사용자가 그대로 쳐야 하는 문자열이다.
- 명사형으로 끝낸다 (`… 수정`·`… 추가`). 목록으로 읽히기 위한 것이다.
